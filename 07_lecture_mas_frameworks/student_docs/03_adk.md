# Google ADK — рантайм, стан, граф

Гілка `03_adk/`. Основна лінія — `g1 → g2 → g3`, далі один бонус.

| Файл | Про що | Статус |
|---|---|---|
| `g1_agent.py` | агент, Runner, Session, потік подій | основне |
| `g2_pipeline.py` | двоє послідовно: `output_key` → `session.state` | основне |
| `g3_workflow.py` | граф `Workflow`: маршрут вирішує код | основне |
| `g3b_transfer.py` | передача управління: маршрут вирішує модель | **бонус** |
| `trace_llm.py` | побачити самі запити до моделі | **бонус**, див. [04_bonus_trace.md](04_bonus_trace.md) |

---

## g1 — агент, Runner, Session

```bash
python 03_adk/g1_agent.py
```

Опис агента тут найкоротший із трьох: `LlmAgent(name, model, instruction,
tools)`. Інструмент — знову гола функція.

Головна ж відмінність ADK не в описі агента, а в **запуску**. CrewAI повертає
результат, MAF повертає результат, ADK повертає **потік подій**: окремо текст,
окремо виклик інструмента, окремо його відповідь. Через цей самий потік
працюють Dev UI, трасування й оцінка, тому вчитися читати його варто одразу.

У виводі ви побачите рядки на кшталт `[support] викликає get_payments` — це і є
події з потоку, розібрані вручну у функції `run()`.

Ще два обов'язкові об'єкти: `Runner` (рантайм — агент сам себе не виконує)
і `Session` (пам'ять однієї розмови). Вони потрібні навіть для одного агента.
Багатослівніше за конкурентів, зате явно.

Зверніть увагу на два різні текстові поля: `instruction` читає сама модель,
а `description` — **інші агенти**, коли обирають, кому делегувати. У `g3b`
це поле раптом почне впливати на маршрут.

Заміряний прогін: **2 виклики, 592 prompt-токени**.

## g2 — двоє послідовно

```bash
python 03_adk/g2_pipeline.py
```

Третій фреймворк — третій механізм передачі даних, і на цьому кроці порівняння
замикається:

| | що фізично їде далі |
|---|---|
| CrewAI | текст результату попередньої задачі |
| Agent Framework | уся розмова цілком |
| **ADK** | **одна іменована комірка `session.state`** |

Перший агент пише результат у `output_key="investigation"`, другий підставляє
його у свою інструкцію як `{investigation}`. Тобто ми точно контролюємо, що саме
побачить наступний: не всю історію, а рівно одне поле.

Передбачуваність тут максимальна з трьох — ціною того, що кожен зв'язок
доводиться описувати руками. Ключа в стані немає — буде помилка, і це добре:
зв'язок явний, а не «на удачу».

Заміряний прогін: **4 виклики, 1 890 токенів**.

`SequentialAgent` у версії 2.7 ще працює, але вже позначений `@deprecated`
на користь нового `Workflow` — його дивимось на кроці 3. Це не прикрість,
а тема заняття: фреймворки живуть близько вісімнадцяти місяців, парадигми
довше. Таблиця відповідностей старого API новому —
у [`VERSIONS.md`](VERSIONS.md).

## g3 — граф, де маршрут вирішує код

```bash
python 03_adk/g3_workflow.py
```

CrewAI на кроці 3 віддав маршрут менеджеру-LLM, MAF — оркестратору-LLM.
ADK 2.x пропонує протилежне: `Workflow` — це явний граф вузлів і ребер,
де розгалуження робить звичайна Python-функція.

Вузол `check_policy` не звертається до моделі взагалі. Він читає суму й ліміт
і виставляє `ctx.route` — «повертаємо самі» або «ескалюємо людині».

Порівняйте виклики LLM із кроком 3 у двох інших фреймворках:

| | крок 3 |
|---|---|
| CrewAI (менеджер-LLM) | 9–36, залежно від прогону |
| Agent Framework (оркестратор-LLM) | 9 |
| **ADK (функція)** | **4** |

Чотири — рівно стільки ж, скільки на кроці 2. На координацію витрачено нуль.
І, на відміну від верхнього рядка, це число те саме на кожному прогоні.

**Спробуйте самі:** зменште `REFUND_LIMIT_USD` у `common.py` до 10 і запустіть
ще раз. Граф піде іншою гілкою (49.99 > 10 → до людини), і жоден виклик LLM
на це не витратиться. Результат повторюваний: той самий вхід дає той самий
маршрут, скільки не запускай.

Чесна засторога, щоб порівняння не було кривим: `Workflow` розв'язує **іншу**
задачу, ніж ієрархія CrewAI. Він добре працює там, де маршрут відомий
заздалегідь і просто має гілки. Коли маршрут справді невідомий, граф
не допоможе — тоді дивіться `g3b`.

## g3b — бонус — той самий маршрут, але обирає модель

> **Бонус.** Друга половина відповіді на питання кроку 3. Дуже рекомендую,
> якщо основна драбина вже зрозуміла, але на розуміння кроків 1–3 не впливає.

```bash
python 03_adk/g3b_transfer.py
python 03_adk/g3b_transfer.py --limit 10    # гілка «до людини»
```

Питання кроку 3 — «хто обирає маршрут», і в ADK є **обидві** відповіді. `g3`
показав кодову, цей файл — модельну, ту саму, що в `c3` і `m3`. Графа тут
немає зовсім: колеги лежать у `sub_agents`, правило ліміту написане словами
в інструкції.

Механізм називається **передача управління**: фреймворк сам додає моделі
інструмент `transfer_to_agent(agent_name)`. У виводі його видно буквально,
а після нього змінюється автор подій — це і є момент передачі:

```
[support_router] викликає get_payments
[support_router] Сума 49.99 USD не перевищує 100.00 USD, передаю оператору повернення.
[support_router] викликає transfer_to_agent
[refund_operator] викликає refund
```

Саме тут вперше працює `description` із кроку 1: ціль передачі модель обирає
**за описом колеги**, інших відомостей про нього в неї немає. Поганий
`description` ламає маршрут — і це не метафора, а спосіб зламати демо
за десять секунд.

Свобода моделі при цьому обмежена кодом: перелік `sub_agents` задаємо ми,
а звузити його ще більше можна прапорцями `disallow_transfer_to_parent`
і `disallow_transfer_to_peers`. Різниця з `g3` не «код проти моделі», а де саме
проходить межа: у графі оголошено все, включно з умовою, тут — лише склад
учасників.

| прогін | викликів LLM | токенів prompt |
|---|---|---|
| `g3` (граф, вирішує код) | 4 | 1 440 |
| `g3b` (передача, вирішує модель) | 4 | ~2 500 |
| `g3b --limit 10` (до людини) | 3 | ~1 800 |

Викликів не побільшало — на двох кроках handoff дешевий. Дивитись треба на
**prompt-токени**: у системний промпт приїхали описи колег і сам
`transfer_to_agent`, а після передачі історія їде до наступного агента цілком.
Про це ж попереджає рядок, який ADK друкує перед банером: без
`context_cache_config` кожна передача міняє префікс промпту, тож кеш не працює
і промпт надсилається наново.

Ще одна відмінність, менш помітна: після передачі колега бачить **історію
розмови**, а не іменовану комірку `session.state`. Тому `refund_operator` тут
описаний заново, без підстановки `{investigation}` — механізм передачі даних
змінився разом із механізмом маршруту.

**Спробуйте самі:** запустіть той самий прогін три-чотири рази. Рано чи пізно
модель відхилиться від регламенту — оформить повернення сама, не передавши
роботу, або піде до людини при сумі в межах ліміту. Це не поломка демо,
а його зміст: у `g3` порушити регламент неможливо за конструкцією, тут — лише
за домовленістю.

## Як це називалося раніше

Код у стилі конспекту (`LlmAgent` + `SequentialAgent` + `output_key` + шаблон
`{research}`) на 2.7.0 працює, але `SequentialAgent` уже позначений
`@deprecated`. Демо навмисно показує обидва API: `g2` — старий, `g3` — новий
графовий `Workflow`. Таблиця «ADK 1.x → 2.7» — у [`VERSIONS.md`](VERSIONS.md).
