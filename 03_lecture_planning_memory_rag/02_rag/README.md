# RAG — демо до Лекції 3 (22 хв)

Продовження демо памʼяті (`../01_memory/`), а не окрема тема. У DevMate архів
сесій шукався повнотекстово, і в `../01_memory/docs/hermes-mapping.md` зафіксовано
його провал: `/search` не знаходить «таймзони», бо в архіві записано
«таймзонами».

Міст у RAG звідси й будується:

> пошук по словах промахується на словоформах і синонімах → потрібен пошук по
> змісту → раз шукаємо в чужому тексті, він недовірений → той самий сканер,
> що захищав памʼять.

Корпус — ті самі девʼять нотаток агента. Домен не змінюється, змінюється
тільки спосіб пошуку.

## Файли

| Файл | Ідея | Що на екрані |
| --- | --- | --- |
| `r1_keyword_vs_embeddings.py` | Пошук по словах проти пошуку по змісту + чесна зворотна сторона | `[СЛОВОФОРМА] [СИНОНІМИ] [ПАСТКА]`, оцінки числами |
| `r2_traditional_rag.py` | Класичний RAG: `query → top-k → generate` з перевіркою цитат | `[RETRIEVE] [PROMPT] [ANSWER] [CITE] ok/FAIL`, `[COST] 1` |
| `r3_agentic_rag.py` | Агент сам вирішує, оцінює і переформульовує | `[ROUTE] [RETRIEVE] [GRADE] [REWRITE] [GENERATE]`, `[COST] 5` |
| `r5_poisoned_corpus.py` | Знайдене — недовірений ввід. Без мережі | `[RETRIEVE] [SCAN] ЗАБЛОКОВАНО` |
| `r4_rerank.py` | **Не на лекції**, домашнє завдання (див. нижче) | `[ДО] [ПІСЛЯ]` |
| `r6_vectordb.py` | Векторна БД: як виглядає API і що вона дає понад косинус | `[API] [QDRANT]/[MANUAL] [FILTER]` |
| `corpus.py`, `llm.py` | Спільні корпус, два пошуки, виклик LLM з лічильником | — |
| `build_vectors.py` | Разовий підрахунок `vectors.json`. На лекції не запускається | — |

## Запуск

```bash
cp ../.env.example ../.env      # вписати OPENAI_API_KEY
pip install requests python-dotenv
python r1_keyword_vs_embeddings.py
python r2_traditional_rag.py
python r3_agentic_rag.py
python r5_poisoned_corpus.py
```

Порядок показу — саме такий: r1 ставить проблему, r2 дає базове рішення,
r3 показує його дорогу альтернативу, r5 закільцьовує годину на безпеці.

## Чому вектори лежать у файлі

`vectors.json` порахований заздалегідь (`build_vectors.py`, модель `bge-m3`
через Ollama). На лекції пошук не робить **жодного** мережевого виклику:
миттєво, однаково при кожному запуску, не залежить від чужого провайдера.
Ембединги в аудиторії не рахуються взагалі — питання «локально чи ні» знято.

Перерахувати кеш (наприклад, після правки корпусу):

```bash
ollama pull bge-m3 && python build_vectors.py
```

Два уточнення, які варто знати заздалегідь:

- **r1, r5 і перший етап r4 не потребують мережі взагалі.** r2 і r3 ходять до
  LLM — це їх суть, кеш векторів тут ні до чого.
- **У r3 запит після `[REWRITE]` породжує модель на льоту**, тож вектора для
  нього в кеші може не виявитись. Замірено: на `temperature=0` модель чотири
  прогони поспіль видає те саме формулювання, і воно закешоване. Якщо скаже
  інакше — вектор порахується живцем через `EMBED_BASE_URL`, а якщо мережі
  немає, скрипт надрукує зрозуміле повідомлення і зупиниться, без трейсу.

Модель `bge-m3` обрана не випадково: `nomic-embed-text` на українському
корпусі провалює головну сцену — на запит «таймзони» потрібна нотатка не
потрапляє навіть у top-3.

## Що показувати голосом

- **r1, сцена 3** — обовʼязкова. Два протилежні запити («чим запускати тести» і
  «чим **НЕ** запускати тести») дають ту саму пару документів із близькими
  оцінками. Вектор кодує тему, а не заперечення: близькість ≠ правильність.
- **r2, `[CITE]`** — цитата це адреса (`doc_id`), а не ввічливість. Підставну
  цитату ловить код, а не читач.
- **r3, хвіст відповіді** — у контекст потрапляє другий документ (`d4` про
  unittest), і модель слухняно приплітає його до відповіді, хоч питали не про
  тести. Це не баг демо, а причина, чому в r2 стоїть перевірка цитат: контекст
  «поруч по змісту» модель вважає дозволом говорити.
- **r3, `[COST]`** — 5 викликів проти 1 у r2. Agentic RAG **не завжди кращий**:
  при стабільному корпусі й чітких запитах traditional + reranking дає
  відповідь дешевше. Звідси й посилання на домашнє r4.
- **r5** — інʼєкція приходить не лише від користувача, а й з корпусу, і захист
  від неї той самий: `scan()` з `../01_memory/devmate/safety.py`, підключений
  через `sys.path`, той самий файл, без копії.

- **r6** — якщо лишився час: як виглядає прив'язка до векторної БД. Сцена
  `[SWAP]` (оцінки Qdrant збігаються з ручним косинусом) і сцена `[FILTER]`
  (той самий вектор запиту, різні дозволені множини документів).

Якщо відстаємо: ріжеться спершу сцена 3 в r1, потім r5.

## Векторна БД: `r6_vectordb.py`

```bash
pip install qdrant-client
python r6_vectordb.py
```

Embedded-режим (`QdrantClient(":memory:")`): ані сервера, ані Docker, ані
мережі. Персистентність — `path="./qdrant_data"`, справжній сервер —
`url="http://..."`; решта коду не змінюється.

**Ембединги сховище не рахує.** Воно приймає готовий список чисел, і чия це
модель — йому байдуже. Тому в колекцію їдуть ті самі вектори з `vectors.json`,
що їх використовує `search_semantic()`. Дві умови обовʼязкові: документи й
запити ембеднуті **однією** моделлю, і `size` колекції дорівнює розмірності
цієї моделі (bge-m3 → 1024). Метрика `Distance.COSINE` узгоджена з тим, як
модель навчали; вектори bge-m3 уже нормовані (довжина = 1.000), тому `DOT` дав
би ті самі числа.

Чесний результат демо: на девʼяти документах БД **не дає** ні швидкості, ні
кращої видачі — оцінки збігаються з ручним косинусом до третього знаку. Дає
вона інше: індекс HNSW замість повного перебору, фільтр по payload як частину
запиту, персистентність, конкурентний запис.

Фільтр — єдине, чого ручний `cosine()` не вміє в принципі: щоб відсікти чуже,
йому довелося б спершу порахувати схожість із чужим. Продовження цієї сцени —
`../03_langgraph/devmate_lg/vector_store.py`, де фільтр стоїть по `tenant` і
береться з `Context` агента.

## Домашнє завдання: `r4_rerank.py`

Reranking на лекцію не помістився: два списки по пʼять рядків читаються з
листа не гірше, ніж зі сцени. Тому — самостійно.

**1. Встановити** (тільки для цього завдання):

```bash
pip install flashrank
python r4_rerank.py
```

Перший запуск викачає модель (~22 МБ) у `./flashrank_cache`.

**2. Очікуваний вивід:**

```
[QUERY] how do I make a long running task survive a service restart

[ДО]    d7=0.528  d1=0.481  d3=0.446  d2=0.431  d6=0.423
[ПІСЛЯ] d1=5.8e-05  d7=1.5e-05  d3=1.5e-05  d2=1.5e-05  d6=1.5e-05
```

Правильна нотатка `d1` (checkpointer) у векторному пошуку була другою —
reranker підняв її на перше місце. Оцінки двох етапів між собою не
порівнюються: косинус — це кут між векторами, оцінка reranker'а — вихід
класифікатора. Порівнюється **тільки порядок**.

Запит тут той самий, на якому в r3 промахнувся перший retrieval і довелося
платити за гілку `[REWRITE]`. Головне питання завдання — чи вистачило б
reranking'а замість неї.

**3. Завдання** — у блоці «Твоя черга» в кінці файлу: підібрати `max_length`
під реальну довжину query+passage і поміряти час; підставити український
корпус і побачити, як англомовна ms-marco перестає розрізняти кандидатів;
порахувати ціну rerank'а проти пʼяти викликів LLM у r3.
