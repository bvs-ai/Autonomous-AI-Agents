# Лекція 6 — надійність агентів. Демо-код для студентів

Сім запускаваних скриптів. Кожен показує **один** патерн надійності і працює
самостійно: без мережі, без LLM, без API-ключів. Зовнішні сервіси — детерміновані
заглушки, тому вивід однаковий на кожному запуску, і його можна порівнювати
з тим, що ви бачили на занятті.

Читати варто в порядку номерів: `r1 → r2 → r3 → r3b → r4 → r5 → r6`. Кожен
наступний спирається на попередній, а останній збирає все докупи.

## Встановлення

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python r1_taxonomy_retry.py tenacity     # перевірка, що все живе
```

## r1 — таксономія помилок і bounded retry

```bash
python r1_taxonomy_retry.py naive       # ретраїмо все підряд -> спалений бюджет
python r1_taxonomy_retry.py tenacity    # @retry тільки на TransientError
python r1_taxonomy_retry.py permanent   # 404: жодного повтору, миттєва відмова
```

Фундамент усієї теми: помилки треба **класифікувати до того**, як вирішувати
питання повтору. `TransientError` (таймаут, 5xx, 429) варто повторити,
`PermanentError` (404, невалідний аргумент) — ніколи, скільки не повторюй,
відповідь буде та сама.

Дивіться на лічильник спалених токенів: кожна спроба тягне в модель повний
контекст. Ретрай 404 у режимі `naive` коштує 12 000 токенів замість 4 000 —
і не дає нічого.

Порівняйте ручний retry і `tenacity`: політика повторів має жити **окремо** від
бізнес-логіки. Зверніть увагу на `stop_after_attempt` (ретрай завжди обмежений),
`wait_exponential_jitter` (без jitter усі клієнти повторюють синхронно і добивають
сервіс) і `reraise=True`.

## r2 — fallback як ланцюг пріоритетів

```bash
python r2_fallback.py healthy    # основна модель відповідає -> degraded=False
python r2_fallback.py            # основна модель недоступна -> йдемо ланцюгом
python r2_fallback.py all-down   # впало все: default + ескалація
```

Fallback — це не «ще один повтор тієї самої операції», а перехід на **інший
шлях**: основна модель → дешевша модель → кеш → безпечний default.

Головна теза, заради якої написаний файл: небезпечний не сам fallback, а
**мовчазний**. Якщо запасне значення їде далі без мітки, наступний агент приймає
його за факт — саме так починається каскад. Тому кожен рівень повертає
`degraded` / `needs_human`, і цей прапорець їде далі в state.

У режимі `all-down` автоматичний платіж блокується: система чесно каже «не
порахувала», а не «ризик нульовий».

## r3 — бюджети: кроки, токени, час

```bash
python r3_budget.py full      # бюджети просторі: агент доходить до мети (done)
python r3_budget.py steps     # впирається в ліміт кроків
python r3_budget.py tokens    # першим вичерпається токеновий бюджет
python r3_budget.py time      # обидва ліміти цілі, але вийшов час
```

Один і той самий цикл агента з трьома різними лімітами зупиняється на **різному
кроці** — це і доводить, що три виміри незалежні і потрібні всі три.

Два моменти в коді:

- бюджет лежить у state **плоскими полями** (`current_step`, `tokens_used`,
  `started_at`), а контролер перестворюється з них на початку вузла. Причина:
  state серіалізується чекпойнтером, мутабельний обʼєкт ламається на
  паралельних гілках;
- вичерпаний бюджет — **не помилка**, а `status: degraded` плюс частковий
  результат. Викидати вже знайдене — антипатерн.

Режим `full` тут для контрасту: бюджет — це аварійний обмежувач, а не штатний
спосіб завершити роботу.

## r3b — два рівні таймаутів

```bash
python r3b_timeouts.py
```

Продовження теми часу з `r3`. Локальний таймаут (один запит, 0.5 с) жодного разу
не спрацював, а операція все одно впʼялася в глобальний дедлайн 1.0 с — бо
**таймаути не складаються**: з ретраями тривалість операції дорівнює
«спроби × (запит + пауза)» і не обмежена нічим, доки ви не поставите окремий
дедлайн на всю бізнес-операцію.

Зверніть увагу, що `TimeoutError` ловиться **зовні** блоку
`async with asyncio.timeout(...)`.

## r4 — durable execution + ідемпотентність

```bash
python r4_idempotency_durable.py unsafe   # resume -> ДРУГИЙ платіж на 50 000
python r4_idempotency_durable.py safe     # той самий resume, платіж один
```

Найважливіший файл заняття. Агент платить постачальнику, вузол `charge` пише
в «банківський реєстр» і одразу після цього процес падає. Чекпойнтер дає resume —
але вузол після resume стартує **з початку**, тому переказ виконується вдруге:
100 000 UAH замість 50 000.

Висновок, який треба забрати: чекпойнтер сам по собі **не рятує** від дублювання
side effect'ів. Рятує `idempotency_key`, згенерований **один раз вище за течією**
(детермінований `uuid5` від номера рахунку, а не `uuid4` всередині вузла — інакше
після resume ключ буде новий і захист не спрацює).

Запустіть обидва режими підряд і подивіться, що лежить у `bank_ledger.json`
після кожного: це стан **зовнішньої** системи, його ніхто не відкотить разом
зі станом графа.

## r5 — circuit breaker

```bash
python r5_circuit_breaker.py off        # тільки retry: довбимо мертвий сервіс
python r5_circuit_breaker.py on         # retry + breaker
python r5_circuit_breaker.py taxonomy   # валідаційна помилка НЕ відкриває circuit
```

Retry лікує **одиничний** збій. Коли сервіс ліг цілком, retry перетворюється на
підсилювач навантаження — потрібна памʼять про стан сервісу **між** викликами.

Три стани і одне рішення в кожному: `CLOSED` (пропускаємо все, рахуємо збої
поспіль), `OPEN` (не пропускаємо нічого, поки не мине cooldown), `HALF_OPEN`
(пропускаємо одну пробу). Мнемоніка: це електричний автомат, а не двері —
`CLOSED` означає «коло замкнуте, струм іде, все працює».

Порівняйте ціну двох режимів на тому самому коді:

| | `off` | `on` |
|---|---|---|
| звернень до сервісу | 17 | **11** |
| токенів | 68 000 | **44 000** |
| час | 6.66 s | **5.16 s** |

Режим `taxonomy` — пряме продовження `r1`: чотири валідаційні помилки поспіль
при порозі 3 **не** відкривають circuit. Breaker міряє здоровʼя сервісу, а не
кількість невдалих викликів; інакше один агент із кривими аргументами відрізав
би сервіс усім іншим.

Два порядки, які треба запамʼятати: **breaker стоїть НАД retry** (перевірка один
раз на логічну операцію, а не на кожну спробу), і `CircuitOpenError` — це третя
категорія помилок, яку не можна ретраїти: вона й означає «не ходи».

## r6 — композиція патернів

```bash
python r6_reliability_composition.py
```

Фінал: `r1`, `r2` і `r5` разом у графі LangGraph на конвеєрі
`lookup → score → pay`. Тут видно те, чого не видно на окремих патернах:

1. **порядок шарів**: breaker зовні, retry всередині;
2. **таксономія розведена по рівнях**: `TransientError` іде в `retry_policy`,
   `CircuitOpenError` — в `error_handler`, а не один `except` на все;
3. вузол зі side effect (`pay`) свідомо **без** `retry_policy`;
4. прапорець `degraded` їде через state і **змінює рішення** наступного вузла:
   ризик з деградованого джерела не дає провести платіж автоматично.

Три сценарії в одному запуску: ретрай упорався, впала risk-модель (fallback →
на людину), реєстр лежить завжди (ретраї вичерпано → breaker відкрився).

## Що забрати із заняття

Стек надійності будується знизу вгору, і кожен рівень закриває те, чого не
закриває попередній:

1. **класифікуй помилку** — інакше решта не має сенсу (`r1`);
2. **обмежений retry** з jitter — на тимчасові збої (`r1`);
3. **fallback з міткою degraded** — коли повторювати нема сенсу (`r2`);
4. **бюджети кроків/токенів/часу** — щоб агент не крутився вічно (`r3`, `r3b`);
5. **ідемпотентність** — щоб resume не подвоїв платіж (`r4`);
6. **circuit breaker** — щоб не добивати мертвий сервіс (`r5`);
7. **композиція** — усе разом і в правильному порядку (`r6`).

Найчастіша помилка на практиці — почати з пункту 2 і не зробити пункти 1 і 5.
