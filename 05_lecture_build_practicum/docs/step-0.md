# Крок 0 — як улаштований LangGraph

Перед кодом — модель, на яку ляжуть усі десять кроків. Тут нема нічого
складного, але без цих п'яти понять решта буде виглядати магією.

## Агент — це граф, а не «розумний об'єкт»

LangGraph описує роботу агента як **граф**: є вузли (кроки роботи) і ребра
(переходи між ними). Ви описуєте граф, потім компілюєте його, потім
запускаєте.

```python
graph = StateGraph(MessagesState)     # оголосили граф і тип стану
graph.add_node("agent", agent_node)   # вузол = звичайна функція
graph.add_node("tools", tool_node)
graph.add_edge(START, "agent")        # ребро = перехід
graph.add_edge("tools", "agent")
app = graph.compile()                 # отримали об'єкт, який можна запускати
app.invoke({"messages": [...]})
```

Порівняйте зі звичайним кодом: ви б написали `while True:` з `if`-ами
всередині. LangGraph просить те саме, але **описом**: цикл — це ребро, яке
веде назад, умова — це функція на умовному ребрі. Навіщо так складно —
стане зрозуміло на кроках 7 і 9: граф, описаний деклативно, можна зберігати
на диск, зупиняти посеред виконання й продовжувати пізніше. Зі звичайним
`while` так не вийде.

## Стан — спільний словник

Усі вузли працюють з одним об'єктом — **станом графа**. Це `TypedDict`,
тобто звичайний словник з описаними полями:

```python
class GuardedState(TypedDict):
    messages: Annotated[list, add_messages]
    step_count: int
    start_time: float
```

`MessagesState` (використовується в кроках 3, 8, 9) — це готовий стан з
одним-єдиним полем `messages`.

## Вузол повертає не стан, а зміну

Головне правило, яке спочатку дивує:

```python
def agent_node(state: MessagesState) -> dict:
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}      # ← не весь стан, а тільки те, що додалось
```

Вузол **не змінює** `state` на місці. Він повертає словник з тими полями, які
хоче оновити, а рушій сам об'єднує це зі станом. Ніяких
`state["messages"].append(...)`.

## Редьюсер — правило об'єднання

Як саме об'єднати — вирішує **редьюсер**, вказаний в анотації типу:

```python
messages: Annotated[list, add_messages]   # ← додати до списку
step_count: int                            # ← без анотації: просто перезаписати
```

- `add_messages` — «дописати нові повідомлення в кінець» (і замінити ті, у
  яких збігається `id`);
- немає анотації — **перезапис**: вузол повернув `{"step_count": 3}`, у стані
  стало 3.

Через це в кроці 5 траєкторія оновлюється так:

```python
traj = state.get("trajectory", [])   # прочитали
traj.append({...})                    # доповнили
return {"trajectory": traj}           # повернули цілком
```

Якби на `trajectory` стояв редьюсер-додавання, вистачило б повернути один
новий запис.

## Повідомлення — це і є «мислення» агента

Усе, що агент зробив, лежить у списку `messages`. Чотири типи:

| Тип | Хто створює | Що означає |
|---|---|---|
| `SystemMessage` | код | інструкція агентові, підставляється першою |
| `HumanMessage` | користувач | запит |
| `AIMessage` | модель | текст відповіді **та/або** `tool_calls` |
| `ToolMessage` | `ToolNode` | результат інструмента |

Ключовий момент: **`AIMessage` з непорожнім `tool_calls` — це не відповідь, а
заявка**. Модель каже: «викличте `calculator` з аргументом `2+2`». Сама вона
нічого не виконує. Виконує звичайний Python-код (вузол `tools`), а результат
повертається в діалог як `ToolMessage`.

```python
# так виглядає стрічка після одного виклику інструмента:
[HumanMessage("Скільки буде 2+2?"),
 AIMessage(content="", tool_calls=[{"name": "calculator", "args": {"expression": "2+2"}, "id": "abc"}]),
 ToolMessage(content='{"status": "ok", "result": 4}', tool_call_id="abc"),
 AIMessage(content="2 + 2 = 4")]
```

Два наслідки, до яких ми повертатимемось увесь час:

1. **Аргументи інструмента вигадала модель.** Це недовірені дані, їх треба
   перевіряти (крок 2).
2. **Кожній заявці має відповідати рівно один `ToolMessage`** з тим самим
   `tool_call_id`. На цьому побудована відмова оператора в кроці 9.

## Умовне ребро — єдине місце, де ухвалюється рішення про маршрут

```python
graph.add_conditional_edges(
    "agent",
    tools_condition,                    # функція: подивитись на стан і повернути мітку
    {"tools": "tools", END: END}        # мітка → куди йти
)
```

`tools_condition` дивиться на останнє повідомлення: є `tool_calls` — повертає
`"tools"`, немає — `END`. Функція повертає **мітку**, а таблиця перетворює
мітку на вузол. У кроці 9 ми напишемо таку функцію самі, бо там потрібні три
варіанти замість двох.

## Що з цього треба запам'ятати

- Граф = вузли + ребра, описується, потім компілюється.
- Вузол — функція `стан → словник зі змінами`.
- Як об'єднувати зміни, вирішує редьюсер (`add_messages` чи перезапис).
- Модель не виконує інструменти, вона їх **просить**.
- Цикл агента — це ребро, що веде назад; виходить агент тоді, коли модель
  відповіла текстом без `tool_calls`.
