# CrewAI — метафора команди

Гілка `01_crewai/`. Основна лінія — три кроки: `c1 → c2 → c3`. Далі три
бонусні файли, кожен окремо й у будь-якому порядку.

| Файл | Про що | Статус |
|---|---|---|
| `c1_agent.py` | агент, роль, інструмент | основне |
| `c2_pipeline.py` | двоє послідовно: `Task.context` | основне |
| `c3_hierarchical.py` | ієрархія: маршрут обирає менеджер-LLM | основне |
| `c3b_conditional.py` | розгалуження без менеджера | **бонус** |
| `c4_flow.py` | `Flow`: маршрут описано кодом | **бонус** |
| `c5_declarative.py` | та сама команда, описана конфігом | **бонус** |
| `trace_llm.py` | побачити самі запити до моделі | **бонус**, див. [04_bonus_trace.md](04_bonus_trace.md) |

---

## c1 — агент і роль

```bash
python 01_crewai/c1_agent.py
```

CrewAI описує агента не системним промптом, а трьома полями: `role`, `goal`,
`backstory`. Виглядає як метафора «команди людей».

**Демо друкує промпт, який фреймворк склав із цих трьох полів.** Це головне,
що варто побачити на кроці 1: жодної магії ролей немає, є генератор тексту.
Прочитайте надрукований промпт і знайдіть у ньому свій `backstory` — після
цього стає зрозуміло, чому від формулювання реально залежить поведінка.

Зверніть увагу на обгортку інструмента: `@tool("Get Payments")`. CrewAI —
єдиний із трьох, кому потрібен декоратор; у двох інших та сама функція йде
голою.

Заміряний прогін: **2 виклики LLM, 722 prompt-токени**. Це базова ціна кроку:
один виклик на рішення викликати інструмент, другий — на формулювання
відповіді.

## c2 — двоє послідовно

```bash
python 01_crewai/c2_pipeline.py
```

Питання кроку одне: **що саме другий агент отримує від першого?**

Відповідь у CrewAI — `Task.context`: текст результату першої задачі дослівно
підклеюється у промпт другої. Ніякої спільної пам'яті, ніякого обміну
об'єктами — лише рядок, який поїхав у наступний запит до моделі.

Демо друкує цей рядок окремим блоком. Побачивши його, легко зрозуміти дві
речі: чому пайплайн ламається, коли перший агент відповів розпливчасто,
і чому за кожну передачу ми платимо токенами двічі.

Зверніть увагу й на розподіл інструментів: `support_agent` уміє тільки читати
виписку, `refund_agent` — тільки повертати кошти. Розділення ролей тут не
заради красивої метафори, воно звужує права кожного учасника.

Заміряні прогони розійшлися: **4 виклики / 1 458 токенів** і **8 викликів /
2 888 токенів**. Розбіжність не помилка: агент сам вирішує, скільки разів
подумати вголос перед відповіддю.

## c3 — ієрархія і її ціна

```bash
python 01_crewai/c3_hierarchical.py     # найдорожчий скрипт демо
```

Тут ми **не** задаємо порядок роботи. Є відділ із трьох ролей, є одна задача —
і менеджер (окремий агент, якого CrewAI створює сам) вирішує, кого залучити.

У коді відмінність від `c2` крихітна: у задачі зникло поле `agent=`, а
`Process.sequential` змінився на `Process.hierarchical`. Дві правки.

Ціна не крихітна:

| | крок 2 | крок 3 |
|---|---|---|
| викликів LLM | 4 | **9** |
| токенів (prompt) | 1 458 | **7 018** |

П'ять зайвих звернень до моделі — це роздуми менеджера «кому далі», а не
робота над тікетом.

І це ще вдалий прогін. Маршрут **недетермінований**: на іншому прогоні того
самого коду ми бачили **36 викликів і 26 956 токенів** — менеджер довше
вирішував, кого залучити. Ваші цифри не збіжаться ні з першою колонкою, ні
з другою, і це не поламаний код, а тема кроку: ціна динамічної координації
не фіксована.

Висновок, заради якого написаний файл: динамічний вибір беруть тоді, коли
маршрут **заздалегідь невідомий**, а не «щоб було гнучко».

## c3b — бонус — умовний перехід без менеджера

> **Бонус.** Поглиблює крок 3. Можна пропустити: основна лінія лекції від
> цього не постраждає.

```bash
python 01_crewai/c3b_conditional.py            # дубль підтверджено, повернення оформлюється
python 01_crewai/c3b_conditional.py --skip     # гілка «повернення не потрібне»
```

На кроці 3 маршрут обирав менеджер, і кожен його вибір коштував виклику LLM.
Але більшість «динаміки» в реальних пайплайнах — це не вибір виконавця,
а одне питання: **чи взагалі потрібен цей крок**. На нього відповідає звичайна
Python-функція.

`ConditionalTask` — це `Task` з полем `condition`: функція, яка бере результат
попередньої задачі і повертає `True`/`False`. `False` — задача не виконується
взагалі, на її місці лишається порожній `TaskOutput`.

Процес при цьому лишається `Process.sequential`, `manager_llm` немає — а
маршрут усе одно розгалужується:

| прогін | викликів LLM | токенів prompt |
|---|---|---|
| звичайний (повернення оформлюється) | 5 | 1 818 |
| `--skip` (крок пропущено) | **3** | 1 085 |
| для порівняння: `c3` (менеджер) | 9–36 | 7 018–26 956 |

Дивіться на рядок `[умова] дубль підтверджено? -> True (жодного виклику LLM)` —
це і є весь «вибір маршруту».

Три обмеження, які варто назвати вголос (перевірено на crewai 1.15.16):

- умовна задача не може бути першою — їй потрібен попередній вивід;
- `condition` бачить лише **останній** вивід, а не весь прогін;
- це пропуск кроку, а не стрибок: назад, вперед через два або в цикл —
  тільки `Flow` (див. `c4`).

Слабке місце теж на видноті: умова парсить вільний текст (`"дубл" in text`).
У проді на такому стику потрібен структурований вивід, а не пошук підрядка.

## c4 — бонус — Flow: маршрут у коді

> **Бонус.** Інший спосіб писати те саме. Читати, якщо збираєтесь будувати
> на CrewAI щось складніше за лінійний пайплайн.

```bash
python 01_crewai/c4_flow.py
```

Крок 2 — це список задач: порядок жорсткий. Крок 3 — ієрархія: порядок обирає
менеджер-LLM. `Flow` — третій варіант між ними: **граф із методів класу, де
розгалуження робить звичайний `if`**.

`@start` / `@listen` / `@router` — це і є весь опис графа; окремої схеми немає.
`@router` повертає **ім'я події**, а не наступний метод, і той, хто на неї
підписаний, відпрацює. Стан живе в `self.state` — типізованому об'єкті, а не
в тексті, який їде далі.

| | хто обирає гілку | ціна вибору |
|---|---|---|
| `c2` | ніхто, порядок у списку задач | 0 |
| `c3` | менеджер-агент | +5…+32 виклики LLM |
| **`c4`** | **`if` у методі `decide`** | **0** |

Заміряний прогін: **4 виклики, 1 282 токени** — стільки ж, скільки на кроці 2,
хоча маршрут тут обчислюється в рантаймі. Гілка `no_refund` не викликає модель
жодного разу.

Висновок кроку: **динаміка маршруту й ціна у викликах LLM — не одне й те саме.**
Платити моделлю за вибір треба лише там, де умову неможливо записати кодом.
Вузол графа при цьому спокійно піднімає всередині себе власний маленький Crew —
саме так і будують реальні застосунки на CrewAI.

Слабке місце варто побачити: ID платежів дістаються з відповіді через
`re.findall(r"PAY-\d+")`. Працює, поки модель згадує їх у тексті; у проді тут
потрібен структурований вивід, а не regex по вільному тексту.

## c5 — бонус — та сама команда, описана конфігом

> **Бонус.** Про організацію роботи, а не про механіку агентів. Читати, якщо
> думаєте, як це житиме в проді.

```bash
python 01_crewai/c5_declarative.py
```

Той самий пайплайн, що на кроці 2, але склад команди й задачі лежать у
`01_crewai/c5_crew.json`, а код лише збирає з них об'єкти. Штатний спосіб
CrewAI — YAML-файли `agents.yaml`/`tasks.yaml` плюс `@CrewBase`; тут те саме
зроблено руками, щоб було видно, що ніякої магії немає: словник роз'їжджається
по конструкторах `Agent(...)` і `Task(...)`.

Заміряний прогін: **4 виклики, 1 404 токени** — практично як у `c2`. Це і є
твердження кроку: **декларативний опис не змінює ні рантайм, ні ціну**,
змінюється лише форма опису.

Дивіться, де проходить межа «дані / код». У конфіг ідуть тексти — `role`,
`goal`, `backstory`, `description`. У коді лишаються інструменти (`"tools":
["get_payments"]` — це лише ім'я, функцію підставляє реєстр `TOOLS`) і
параметри безпеки: `max_iter`, `allow_delegation`, модель.

Практичний сенс: у проді так живуть промпти. Правка формулювання ролі перестає
бути комітом у код, конфіг їде на рев'ю окремо, а кілька варіантів під різні
мови чи ринки — це просто кілька файлів. Що ламається: JSON ніхто не валідує —
одруківка в `"agent": "suport"` дасть `KeyError` уже під час складання команди.
