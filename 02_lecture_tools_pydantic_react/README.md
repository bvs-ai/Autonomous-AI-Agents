# Демо до Лекції 2 — Tool/Function Calling та ReAct-агент

Набір мінімальних, але робочих прикладів, що продовжують наскрізний сценарій
лекції 1: **агент підтримки інтернет-магазину**, що працює з `query_orders` /
`check_return_policy`. Лекція 1 була **ознайомленням**: там ми один раз
доторкнулися до tool calling, Pydantic, запобіжників і фреймворку — щоб зібрати
працюючого агента. Тут ті самі теми розбираються **як інженерна дисципліна**:
контракт інструмента, Pydantic v2 як єдине джерело правди, продакшн-обвʼязка,
тестування, безпека і патерн ReAct із керованим циклом.

Тому частина сюжетів свідомо повторюється — але не як відкриття, а як повернення
на глибшому рівні. Де це так, у docstring демо стоїть явна відсилка.

| Тема | Лекція 1 (ознайомлення) | Лекція 2 (цей набір) |
| --- | --- | --- |
| JSON Schema інструмента | `009` — мінімальна: `type` + `description` | `001` — `enum`, `pattern`, `additionalProperties:false` + 5 типів помилок |
| Pydantic | `010`/`010b` — валідація **фінальної відповіді** | `002-004` — контракт **входу і виходу інструмента** + витік даних у помилках |
| Strict / constrained decoding | `010b` — `response_format` для відповіді | `005-006` — strict для **аргументів** інструмента |
| Запобіжники | `011` — `if`и всередині власного `while` | `017-018` — `StopController` як компонент + `safe_tool_node` у графі |
| Allowlist | `011` — захист від помилки моделі | `013` — захист від **атаки** (prompt injection) + чому denylist крихкий |
| Фреймворк | `016` — `create_agent`, «фреймворк дає цикл, а не надійність» | `016` — той самий агент, але видно граф; `018` — куди саме вставляти надійність |
| Structured output фінальної відповіді | `016` — `response_format=ToolStrategy(...)`, структурує **сам агент** | `016` — `with_structured_output()` **окремим кроком після циклу**: менше вимог до рушія провайдера, тому працює там, де `ToolStrategy` дає 400 |

Сценарій навмисно не змінюється між демо: кожен файл — **невеликий крок від
попереднього**, тому видно, що саме додає кожен наступний механізм.

## Швидкий старт

```bash
python -m venv .venv && source .venv/bin/activate

pip install -r requirements.txt             # для всіх демо, крім 016 і 018
pip install -r requirements_langgraph.txt   # додатково для ReAct у LangGraph

cp .env.example .env      # і вписати свій ключ
```

**Без мережі й ключа працюють:** 001-005, 008-015, 017, 019, 020.
**Потребують LLM:** 006, 007, 016, 018.

> ⚠️ **`006` і `007` потребують сильнішої моделі** — з тієї ж причини, що й
> `010b`/`016` у лекції 1: strict tool calling це фіча рушія інференсу, а не
> «розуму» моделі. Слабкий маршрут або поверне 400, або мовчки проігнорує
> `strict` і `parallel_tool_calls`. У `007` це видно як hedging: модель викликає
> обидва інструменти одразу незалежно від описів.

`stop_controller.py` — єдиний модуль без номера: його ділять між собою 012, 017 і
018, і це не випадковість, а те саме, що ми показуємо в 017 (стоп-критерії —
окремий тестований компонент, а не пара `if`ів усередині циклу, як у `011`
лекції 1).

> На відміну від лекції 1, тут демо загорнуті в `if __name__ == "__main__"`:
> інакше не працювали б ані `pytest` (012), ані спільний `stop_controller`.

## Порядок демо

### Шар 1. Інструмент як контракт

| Файл | Що показує |
| --- | --- |
| `001_tool_contract_json_schema.py` | «Закрита» JSON Schema для `query_orders`/`check_return_policy`: `enum`, `pattern`, `additionalProperties:false`. Рукописний валідатор мапує кожен провал на один із 5 типів помилок інструмента (Validation / Execution / Permission / Schema Mismatch / Hallucinated Tool). |

**Ідея шару:** нечіткий контракт — головна причина збоїв агента; помилка теж є частиною контракту.

### Шар 2. Pydantic v2 — валідація входу і виходу

| Файл | Що показує |
| --- | --- |
| `002_pydantic_input_models.py` | Ті самі інструменти як Pydantic-моделі: `Literal` замість вільного рядка, `ConfigDict(extra="forbid")`, `field_validator(mode="before")` для нормалізації `order_id` ДО перевірки `pattern`. |
| `003_pydantic_output_models.py` | Схема виходу, вбудована в реалізацію інструмента: `model_validate()` на сирих даних, `model_dump(mode="json")` на виході. |
| `004_pydantic_error_leakage.py` | Текст `ValidationError` іде МОДЕЛІ в контекст — а Pydantic за замовчуванням цитує в ньому значення поля (номер картки). `hide_input_in_errors=True` + власна redaction до `loc`+`msg`. |

**Ідея шару:** одна модель = схема + runtime-валідатор + документація. Pydantic за
замовчуванням `extra="ignore"` — для інструментів це свідомо міняють на `"forbid"`.

> ⚠️ **Нюанс, який легко проґавити:** `Field(pattern=...)` перевіряється Pydantic
> РАНІШЕ, ніж `field_validator` у режимі за замовчуванням (`mode="after"`). Якщо
> validator має нормалізувати рядок (`"a-1001"` → `"A-1001"`) ДО перевірки
> pattern — потрібен `mode="before"`, інакше нормалізація ніколи не спрацює.

### Шар 3. Structured tool calling у провайдера

| Файл | Що показує |
| --- | --- |
| `005_pydantic_to_strict_schema.py` | `model_json_schema()` — ще НЕ strict-схема: у strict усі поля мають бути в `required` (опціональність — через тип з `null`), а `default` не допускається. Маленький адаптер `to_strict()`. Без мережі. |
| `006_openai_strict_tool_calling.py` | Той самий агент, що в 009 лекції 1, але схема з Pydantic через `to_strict()`, `strict=True` і `parallel_tool_calls=False` — гарантія через constrained decoding, а не «гарний» промпт. |
| `007_tool_descriptions_as_policy.py` | Схема задає граматику, description — семантику. Два інструменти з ОДНАКОВОЮ схемою (повернення vs гарантія), правильний вибір залежить від правила, якого модель не вгадає. Міні-eval: точність вибору + hedging для «розмитих» і «чітких» описів. |

**Ідея шару:** strict гарантує *валідні аргументи*, але не *правильний інструмент* —
за вибір відповідає description, і його треба вимірювати, а не сподіватися.

### Шар 4. Production-обвʼязка

| Файл | Що показує |
| --- | --- |
| `008_tool_wrapper_timeouts_retries.py` | `tool_wrapper` навколо інструмента, що «ходить» у нестабільний сервіс: покомпонентний `httpx.Timeout` (connect/read/write/pool), `tenacity` з exponential backoff + jitter, graceful degradation — структурована помилка замість краху. |
| `009_retry_policy_what_not_to_retry.py` | Політика повторів у коді: 429/503/таймаут повторюємо, 400/401/404 і `ValidationError` — ні. Різниця видна по кількості звернень до API: 3 проти 1. |
| `010_audit_log_append_only.py` | Append-only журнал: UTC ISO-час, allowlist полів (щоб у журнал не поїхав `auth_token`), `get_entries()` через `deepcopy` — і демонстрація, як shallow-копія дозволила б переписати вже записану подію. |
| `011_structured_logging_json.py` | `StructuredFormatter` — кожен запис логу як JSON-обʼєкт (не рядок для regex), із traceback при помилці. |

> ⚠️ **Класична пастка з `tenacity`:** без `reraise=True` після вичерпання спроб
> піднімається `tenacity.RetryError` (що обгортає останній виняток через
> `__cause__`), а НЕ сам оригінальний виняток. Обидва варіанти показані в тестах
> `012`, а `008` явно ловить `retry_on`, бо використовує `reraise=True`.

### Шар 5. Тестування

| Файл | Що показує |
| --- | --- |
| `012_test_tools.py` | Unit-тести Pydantic-валідації без моків; мок зовнішнього виклику в місці використання; ізоляція мережі через `httpx.MockTransport`; retry-логіка без реальних затримок (`monkeypatch tenacity.nap.sleep`); тести `StopController` — логіку зупинки агента можна покрити тестами, а поведінку моделі ні. |

```bash
pytest 012_test_tools.py -v
```

### Шар 6. Безпека інструментів

| Файл | Що показує |
| --- | --- |
| `013_security_allowlist_vs_denylist.py` | Prompt injection у полі замовлення: allowlist блокує будь-який виклик поза списком незалежно від імені; denylist за патернами обходиться косметичною зміною назви (`purge_order` замість `delete_order`). |

**Ідея шару:** allowlist ми вже писали в `011` лекції 1 — але як захист від
*помилки* моделі. Тут той самий рядок коду розглядається як захист від *атаки*:
помилка випадкова, а атака підбирається — саме тому denylist не працює. Allowlist —
модель повноважень (least privilege), denylist — лише санітарний шар.

### Шар 7. Патерни проєктування інструментів

| Файл | Що показує |
| --- | --- |
| `014_tool_design_patterns.py` | Одна задача трьома способами: **thin** (3 атомарні інструменти, 6 кроків), **smart** (1 крок, уся логіка в коді), **orchestrator** (1 крок агента, але кроки видно у `trace`). Плюс межа застосовності: запит із «довгого хвоста», де виграє саме thin. |

### Шар 8. Інструменти в LangChain

| Файл | Що показує |
| --- | --- |
| `015_langchain_tool_definitions.py` | `@tool` (імʼя/опис/схема з функції) і `@tool(args_schema=...)` з Pydantic-моделлю. `args_schema` працює у два боки: контракт для LLM і рантайм-фільтр — тіло функції не почнеться, якщо аргументи не пройшли `pattern`. |

### Шар 9. ReAct у LangGraph

| Файл | Що показує |
| --- | --- |
| `016_react_agent_langgraph.py` | **Той самий `create_agent`, що в `016` лекції 1**, з тим самим Agent Spec. Тоді це був фінал, тепер — стартова точка: даємо циклу імʼя (ReAct) і дивимось на граф. `get_graph().draw_mermaid()` малює структуру, `.stream()` показує виконання по вузлах — Action (вузол `model`) і Observation (вузол `tools`). Наприкінці — фінальний `ReturnReport` через `model.with_structured_output()`: окремий крок після циклу, опора для домашнього завдання (вузол `formatter`). |
| `017_stop_criteria.py` | Стоп-критерії окремо від графа й без LLM: max_steps, token budget, loop detection — і Sufficiency як єдине «здорове» завершення. Кожну кнопку можна натиснути руками. |
| `018_react_from_scratch_safe_tool_node.py` | Той самий граф руками на `StateGraph` — заради двох речей: `StopController` в умовному ребрі (причина зупинки замість винятку) і `safe_tool_node` замість `ToolNode` (виняток усередині інструмента → `ToolMessage`, а не крах графа). `AgentState` рахує `step_count` і `total_tokens`. |

**Ідея шару:** ReAct — це граф із двома вузлами й умовним ребром. У лекції 1 демо
`016` закінчилося тезою «фреймворк дає цикл, а не надійність — запобіжники з `011`
все одно писати самому». `017`-`018` показують, **куди саме** їх вставляти, коли
цикл більше не твій: в умовне ребро і у вузол інструментів.

> Про API: `create_react_agent` з `langgraph.prebuilt` у LangGraph 1.0 застарів
> саме на користь `create_agent`, який ми використовували ще в лекції 1. У
> туторіалах ви ще зустрінете стару назву — це той самий граф.

### Шар 10. Failure modes і вибір архітектури

| Файл | Що показує |
| --- | --- |
| `019_failure_modes_defense_in_depth.py` | Траєкторія «тижневий звіт» двічі: **версія A** без захисту падає на кроці 1 з `KeyError`; **версія B** проходить усі 7 кроків — галюцинація інструмента, невалідні аргументи, зациклювання, 503, ризик context overflow — і повертає частковий, але валідний звіт. Розвиток сценарію `trap` з `011` лекції 1: там пастка була одна, тут вони йдуть ланцюгом. |
| `020_react_vs_plan_execute.py` | Чистий ReAct дає нестабільну кількість кроків між прогонами; Plan-and-Execute — стабільний, видимий заздалегідь план. |

## Наскрізна лінія

```
001       контракт інструмента як JSON Schema + 5 типів помилок
002-004   Pydantic v2: вхід, вихід і те, що витікає в помилках
005-007   строгий tool calling: адаптер схеми, constrained decoding, description як політика
008-011   продакшн-обвʼязка: тайм-аути, політика retry, audit trail, structured logging
012       тестування: unit без моків, MockTransport, no-sleep retry, стоп-критерії
013       безпека: allowlist проти denylist
014       thin vs smart vs orchestrator — де лежить складність
015       інструменти в LangChain: @tool, args_schema
016-018   ReAct у LangGraph: готовий агент і його граф -> стоп-критерії -> граф руками
019-020   failure modes + defense-in-depth; ReAct проти Plan-and-Execute
```

## Якщо часу мало

Мінімальний трек, що зберігає сюжет: **001 → 002 → 004 → 006 → 007 → 008 → 010 →
013 → 014 → 016 → 017 → 018 → 019**. Решта — самостійно.
