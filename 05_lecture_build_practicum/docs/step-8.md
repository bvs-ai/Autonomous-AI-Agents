# Крок 8 — agentic RAG

`step8_rag.py`, 166 рядків: база документів → векторне сховище → інструмент
`knowledge_search` → агент, який відрізняється від кроку 3 одним елементом
списку інструментів.

## Класичний RAG проти agentic RAG

**Класичний RAG — це конвеєр:** запит → завжди пошук → підстановка знайденого
в промпт → відповідь. Пошук виконується безумовно, до моделі.

**Agentic RAG — це інструмент:** пошук оформлений як звичайний tool, і рішення
шукати (і як сформулювати запит) ухвалює сам агент.

```
Класичний:  запит ──> retriever ──> промпт з контекстом ──> модель ──> відповідь
Agentic:    запит ──> модель ──(чи потрібно?)──> knowledge_search ──> модель ──> відповідь
                            └──(не потрібно)──> відповідь
```

Наслідок видно в демо на четвертому запиті: «Скільки буде 15 * 4?» —
`knowledge_search` **не викликається**. У класичному конвеєрі пошук
відпрацював би все одно, витратив час і засмітив промпт нерелевантними
документами.

## База знань

```python
documents = [
    Document(
        page_content="LangGraph — це бібліотека для побудови агентних систем як графів станів. ...",
        metadata={"source": "lecture_03", "topic": "langgraph"}
    ),
    ...
]
```

Вісім документів, зашитих у код (у реальному проєкті — завантаження з файлів
і нарізання на фрагменти). Але важливе тут інше — **`metadata`**.

Метадані їдуть разом із текстом і повертаються при пошуку. Навіщо:

- **цитованість**: відповідь можна супроводити «джерело: lecture_03»;
- **фільтрація**: `search_kwargs={"filter": {"topic": "hitl"}}` звужує пошук
  без переіндексації;
- **розмежування доступу**: у реальній системі в метадані кладуть власника
  документа. Це єдиний робочий спосіб не віддати чужі дані —
  **ембединги про права доступу нічого не знають**.

Кумедна деталь: вміст документів — це конспект курсу про сам LangGraph. Агент
шукає відповіді про інструменти, якими сам зроблений.

## Векторне сховище

```python
embeddings = GoogleGenerativeAIEmbeddings(model="models/gemini-embedding-001")
vectorstore = Chroma(
    collection_name="course_knowledge",
    embedding_function=embeddings,
    persist_directory=CHROMA_DIR,
)
if vectorstore._collection.count() == 0:
    vectorstore.add_documents(documents)

retriever = vectorstore.as_retriever(search_kwargs={"k": 3})
```

**Ембединги — окрема модель і окремий виклик API.** Не та, що генерує текст.
Її задача — перетворити текст на вектор (сотні чи тисячі чисел), де близькість
векторів означає близькість змісту. Префікс `models/` в імені обов'язковий,
інакше 404.

**`persist_directory`** робить сховище файловим (тека `chroma_db/`). Без нього
Chroma живе в пам'яті й індексується заново щоразу.

**Перевірка `count() == 0` — не дрібниця.** Без неї кожен запуск скрипта додає
ті самі 8 документів наново; після трьох прогонів у базі 24 дублікати, і `k=3`
повертає три копії одного тексту. Індексація — це операція зі станом, і вона
має бути **ідемпотентною** (запустив двічі — результат той самий).

Чесно: перевірка «чи порожньо» — найпримітивніший варіант. Якщо документи
зміняться, вона не спрацює. Надійніше — хеш вмісту в id документа й upsert.

**`k=3`** — скільки документів повернути. Мало — можна не влучити в потрібний,
багато — шум і зайві токени.

Що відбувається під час пошуку: запит теж перетворюється на вектор тією ж
моделлю, далі шукаються найближчі сусіди. Ніякого «розуміння» — лише геометрія.
Звідси типові провали RAG: точні терміни, заперечення й числа шукаються погано;
для цього потрібен гібридний пошук (ключові слова + вектори).

## Пошук як інструмент

```python
class RAGInput(BaseModel):
    query: str = Field(..., description="Пошуковий запит до бази знань", min_length=3)

@tool(args_schema=RAGInput)
def knowledge_search(query: str) -> str:
    """Шукає релевантну інформацію в базі знань курсу (лекції, матеріали).
    Використовуй, коли потрібна інформація про LangGraph, ReAct, Plan-and-Execute,
    Pydantic, checkpointer, agentic RAG або HITL."""
    docs = retriever.invoke(query)
    if not docs:
        return json.dumps({"status": "not_found", "query": query})
    results = [{"content": d.page_content,
                "source": d.metadata.get("source", "?"),
                "topic": d.metadata.get("topic", "?")} for d in docs]
    return json.dumps({"status": "ok", "query": query, "results": results}, ensure_ascii=False)
```

Той самий шаблон, що у п'яти інструментів кроку 2: схема + docstring +
`{"status": ...}`. **У цьому й суть**: RAG перестає бути окремою архітектурою
і стає ще одним рядком у списку інструментів.

**Docstring критичний.** У ньому перелічені теми бази знань. Це єдиний спосіб,
яким модель дізнається, *що* лежить у сховищі: вміст бази вона не бачить,
бачить лише опис інструмента. Поганий опис = інструмент не викликається там,
де потрібен.

> Опис інструмента має описувати не механізм, а **область застосування**.

І зверніть увагу: `query` — це аргумент, який **вигадує модель**. Вона може
переформулювати питання користувача під пошук, розбити його на кілька
запитів, уточнити після невдалого. Це друга відмінність від класичного RAG,
де в retriever їде сирий текст користувача.

## Граф — три рядки різниці

```python
rag_tools = safe_tools + [knowledge_search]
llm_with_rag_tools = llm.bind_tools(rag_tools)

RAG_SYSTEM_PROMPT = SYSTEM_PROMPT + (
    "\nТакож ти маєш інструмент knowledge_search для пошуку в базі знань курсу. ...")
```

Далі — покомпонентна копія графа з кроку 3: ті самі два вузли, той самий
`tools_condition`, те саме ребро назад. **Топологія не змінилась узагалі.**

Відкрийте `step3_react.py` і `step8_rag.py` поруч — різниця в трьох рядках.
Висновок: додати RAG до наявного агента — це +1 інструмент, а не переписування
архітектури.

(Так, вузол і граф тут скопійовані, а не перевикористані. Це зроблено
навмисно, щоб кожен файл читався окремо. У справжньому проєкті ви б написали
фабрику `build_agent(tools, system_prompt)`.)

## Демо

Спершу — **пошук без агента**:

```python
for d in retriever.invoke("checkpointer"):
    print(f"   • [{d.metadata['topic']}] {d.page_content[:70]}...")
```

Це просто функція «текст → документи», жодної магії. І тільки потім над нею
надбудовується агент.

Потім чотири запити:

| Запит | Що має статись |
|---|---|
| «Що таке Plan-and-Execute і чим відрізняється від ReAct?» | `knowledge_search`, влучання у два документи |
| «Як працює SqliteSaver у LangGraph?» | `knowledge_search`, точне влучання |
| «Порахуй 256 * 512 і знайди в базі знань про structured outputs» | **два різні інструменти в одному запиті** |
| «Скільки буде 15 * 4?» | тільки `calculator`, бази знань не торкались |

Останні два — головні. Третій показує комбінування джерел, четвертий доводить
тезу кроку: рішення шукати ухвалює агент.

Зверніть увагу: перший запит не містить слова «checkpointer», але знаходить
потрібний документ — це і є семантичний пошук.

