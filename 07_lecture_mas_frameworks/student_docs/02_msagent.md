# Microsoft Agent Framework — клієнт, middleware, розмова

Гілка `02_msagent/`. Основна лінія — `m1 → m2 → m3`, далі один бонус.

| Файл | Про що | Статус |
|---|---|---|
| `m1_agent.py` | агент, інструкція, middleware | основне |
| `m2_pipeline.py` | двоє послідовно: далі їде вся розмова | основне |
| `m3_groupchat.py` | груповий чат: маршрут обирає оркестратор-LLM | основне |
| `m3b_switch.py` | switch-case на ребрі графа, без оркестратора | **бонус** |
| `trace_llm.py` | побачити самі запити до моделі | **бонус**, див. [04_bonus_trace.md](04_bonus_trace.md) |

У конспекті на цьому місці AutoGen. Він заморожений на 0.7.5, наступник —
Microsoft Agent Framework; таблиця відповідності старих і нових назв —
у [`VERSIONS.md`](VERSIONS.md).

---

## m1 — агент та інструкція

```bash
python 02_msagent/m1_agent.py
```

Та сама задача, що й `c1`, — і одразу три відмінності. Немає
role/goal/backstory: є звичайний рядок `instructions`. Інструменти йдуть
голими функціями з `common.py`. API асинхронний, тому запуск через
`asyncio.run`.

Головне у файлі — **middleware**: функція, крізь яку проходить кожне звернення
до моделі. У CrewAI метрики рахував сам фреймворк, тут — ні, тому лічильник
пишемо самі. Це і є штатне місце, де в MAF роблять логування й трасування.

Там же полагоджено дрібницю, яка інакше вистрелила б на кроках 2 і 3: Gemini
відхиляє запит, що закінчується реплікою моделі (`400 ... Requests ending with
a model turn are not supported`), а в багатоагентній розмові саме так і буває.
Одна правка в одному місці — і всі три кроки працюють.

Зверніть увагу на розділення **клієнт / агент**: клієнт — це «як ходити
в модель», агент — «яка інструкція та які тули». Один клієнт
перевикористовується для всіх агентів, і middleware разом із ним.

Заміряний прогін: **2 виклики, 538 prompt-токенів** — та сама базова ціна,
що й у `c1`.

## m2 — двоє послідовно

```bash
python 02_msagent/m2_pipeline.py
```

Те саме завдання, що й `c2`, — і тут головна різниця двох фреймворків.

CrewAI передавав далі **текст результату**. MAF передає **всю розмову**: список
повідомлень, до якого кожен учасник дописує свої. Другий агент бачить не
переказ, а оригінальні репліки й виклики інструментів першого.

Демо друкує цей ланцюжок цілком — рядок за рядком, із іменами авторів. Це не
реконструкція, а рівно те, що middleware побачив в останньому зверненні
до моделі.

Ціна теж інша: спільна розмова означає, що промпт росте з кожним учасником.
Заміряно **4 виклики, 1 484 токени**. На двох агентах різниця з CrewAI
невелика, на п'ятьох стає визначальною.

## m3 — груповий чат

```bash
python 02_msagent/m3_groupchat.py
```

Черговість не задає ніхто з людей: є троє агентів і **оркестратор** — окремий
агент, який перед кожним ходом дивиться на розмову й вирішує, кому говорити
далі.

Це та сама ідея, що ієрархія в `c3`, але механізм видно чіткіше: оркестратора
ми створюємо самі, звичайним `as_agent`, і його інструкцію видно повністю.
Прочитайте її — маршрут у ній описаний словами. Тобто порядок ми фактично
знаємо, і все одно платимо за те, щоб модель виводила його щоразу заново.

| | крок 2 | крок 3 |
|---|---|---|
| викликів LLM | 4 | **9** |
| токенів (prompt) | 1 484 | **4 356** |

Різниця — робота оркестратора.

Найважливіше в цьому файлі написано в докстрингу, а не в коді: детермінована
альтернатива коштує один рядок. Замість `orchestrator_agent=` передати
`selection_func=` — звичайну Python-функцію вибору наступного. Тоді координація
безкоштовна, але й гнучкості нуль. Один іменований параметр відділяє «вирішує
модель» від «вирішує код».

`max_rounds=5` — запобіжник. Коли цикл завершує модель, ліміт обов'язковий.

## m3b — бонус — switch-case без оркестратора

> **Бонус.** Те саме питання, що в `c3b`, але в MAF. Пропускається без втрат
> для основної лінії.

```bash
python 02_msagent/m3b_switch.py           # дубль підтверджено
python 02_msagent/m3b_switch.py --skip    # гілка Default, повз refund_operator
```

Маршрут тут теж динамічний, але обирає його звичайна Python-функція на ребрі
графа, і коштує це нуль:

```
support ──(дубль підтверджено)──> refund_operator ──> writer
        └──────(Default)──────────────────────────────> writer
```

Заради чого цей файл узагалі існує — різниця з CrewAI. Там умовність усередині
`Crew` бінарна: `ConditionalTask` вміє лише виконатись або ні, а справжнє
розгалуження живе в окремому API (`Flow`). У MAF **граф — це базовий шар**:
`WorkflowBuilder.add_switch_case_edge_group()` розводить повідомлення по різних
виконавцях штатно, а `SequentialBuilder` з кроку 2 і `GroupChatBuilder` з кроку
3 — надбудови над тим самим графом.

| прогін | викликів LLM | токенів prompt |
|---|---|---|
| звичайний | 5 | 1 988 |
| `--skip` (Default) | **3** | 892 |
| для порівняння: `m3` (оркестратор) | 9 | 4 356 |

`Case` перевіряються по порядку, перемагає перший, чия умова дала `True`;
`Default` забирає все інше. Ребра приймають самих агентів — обгортати їх
у власні `Executor` не потрібно.

Слабке місце те саме, що в `c3b`: умова читає вільний текст відповіді. Зверніть
увагу на аргумент умови — `AgentExecutorResponse`, у якому є і відповідь агента
(`.agent_response`), і вся розмова (`.full_conversation`). Тобто в MAF навіть
умова на ребрі бачить усю історію, а не лише останній рядок.

## Як це називалося раніше

AutoGen `autogen-agentchat` 0.7.5 із конспекту переведений у режим підтримки;
Agent Framework 1.14 — його наступник. Три місця, де легко спіткнутися: агент
створюється через `client.as_agent(...)` (а не `create_agent(...)`), параметр
моделі — `model=` (а не `model_id=`), інструмент передається голою функцією.
Повна таблиця відповідностей — [`VERSIONS.md`](VERSIONS.md).
