# Крок 3 — ліміт, який змушує думати

Пам'ять стає по-справжньому скінченною. Але ключове рішення протилежне до
очікуваного: **пам'ять не стискає себе сама**.

## Усе є пакетом операцій

Одиночної гілки коду немає — одна зміна це пакет з однієї операції:

```python
def memory(target: str, operations: list | None = None, **single) -> str:
    return memory_store.apply(target, operations or [single])
```

Пакет застосовується до **копії** списку записів:

```python
def apply(target: str, operations: list[dict]) -> str:
    store = stores.get(target)
    entries = list(store.entries)          # копія
    try:
        results = [_apply_one(entries, op) for op in operations]
    except ValueError as exc:
        return f"ПОМИЛКА: {exc}"

    used = store.size(entries)
    if used > store.limit:
        return _overflow(store, used)      # нічого не збережено

    store.entries = entries                # приймаємо цілком
    store._write()
    return f"{', '.join(results)}. Зайнято {used}/{store.limit} символів."
```

Два наслідки:

**Атомарність.** Помилка в третій операції з чотирьох — і не застосовується
жодна. Оригінальний `store.entries` не змінювався.

**Ліміт перевіряється лише за фінальним станом.** Проміжні стани можуть
перевищувати ліміт скільки завгодно.

## Навіщо це потрібно

Уявіть, що операції були б поодинокими, а пам'ять заповнена. Щоб додати
запис, треба спершу звільнити місце. Але `remove` і `add` — різні виклики, і
між ними модель може відволіктися, вирішити, що вже все зробила, або
просто відповісти користувачу. Пам'ять лишиться без потрібного запису, зате
з видаленим потрібним.

Пакет знімає проблему: один виклик і прибирає, і додає.

```python
memory(target="memory", operations=[
    {"action": "remove",  "old_text": "лекцією"},
    {"action": "replace", "old_text": "Борис", "content": "Борис: викладач, стислі відповіді"},
    {"action": "add",     "content": "Стек демо: Python + SQLite"},
])
```

## Переповнення — це відмова з переліком

```python
def _overflow(store: Store, used: int) -> str:
    listing = "\n".join(f"  {i}. {e}" for i, e in enumerate(store.entries, 1))
    return (
        f"ПОМИЛКА: не вміщується — вийде {used}/{store.limit} символів.\n"
        f"Наявні записи:\n{listing}\n"
        "Повторіть ОДНИМ викликом з масивом operations: приберіть або "
        "скоротіть застаріле і додайте нове разом."
    )
```

Модель отримує не просто «не вміщується», а **список усіх записів** і чітку
інструкцію, що робити далі.

## Чому не автоматичне витіснення

Спокуса зробити «викидаємо найстаріший запис» велика. Але найстаріший запис
— це зазвичай ім'я користувача, записане в першу сесію. Витіснення за
розміром викине найінформативніший запис. Витіснення за частотою звернень
неможливе: ми не знаємо, який запис допоміг моделі відповісти.

Що саме втратило актуальність, знає лише той, хто розуміє зміст. Тому
рішення віддано моделі — а система лише не дає перевищити ліміт.

## Запобіжник від залипання

```python
MAX_FAILURES = 3

if _failures >= MAX_FAILURES:
    return (
        "ПОМИЛКА: пам'ять переповнено, спроби консолідації вичерпано. "
        "Припиніть writes і відповідайте користувачу."
    )
```

Лічильник скидається на межі ходу — `memory.start_turn()` викликається на
початку `run_turn`. Без нього агент здатен витратити весь ліміт ітерацій на
боротьбу з власною пам'яттю і не відповісти взагалі.

## Найцікавіше стається без помилки

Занизьте ліміт до 200 символів і попросіть щось запам'ятати. Часто модель
**не доводить справу до відмови**: побачивши в промпті `[91% — 182/200]`,
вона одразу зливає два записи в один коротший.

Реальний приклад із запуску — замість того щоб додати п'ятий запис, модель
викликала:

```json
{"action": "replace",
 "old_text": "Тести запускаються командою pytest -q",
 "content": "Тести: pytest -q; збірка: make build"}
```

Саме на це й розрахований відсоток у заголовку блоку з кроку 2.
