# Демо до Лекції 1 — Автономні агенти та LLM API

Набір мінімальних прикладів, що вибудовуються в одну лінію: від «сирого» HTTP-запиту до LLM —
до агента з контрактом (Agent Spec) і до того самого агента, зібраного фреймворком.

Наскрізний сценарій усіх агентних демо один і той самий: **агент підтримки інтернет-магазину**
шукає замовлення зі статусом `повернення` і перевіряє, чи вкладаються вони у вікно повернення
(30 днів). Один сценарій навмисно не змінюється — так видно, що саме додає кожен наступний крок.

---

## Швидкий старт

```bash
python -m venv .venv && source .venv/bin/activate

pip install -r requirements.txt             # для всіх демо, крім 016
pip install -r requirements_langchain.txt   # додатково, якщо показуємо 016

cp .env.example .env      # і вписати свій ключ
```

`.env` читається у всіх демо через `python-dotenv`:

| Змінна | Призначення |
| --- | --- |
| `OPENAI_BASE_URL` | базовий URL OpenAI-сумісного API (шлюз, провайдер або Ollama) |
| `OPENAI_API_KEY` | ключ; для Ollama підійде будь-який рядок |
| `LLM_MODEL` | ідентифікатор моделі |

SDK `openai` підхоплює `OPENAI_BASE_URL` і `OPENAI_API_KEY` автоматично — тому в коді
скрізь просто `OpenAI()` без аргументів.

Перемикання на локальну модель — див. розділ [Ollama](#ollama-локальні-моделі):

```bash
cp .env.ollama .env
```

### Залежності по демо

Стандартної бібліотеки Python **не досить**: навіть найпростіші демо тягнуть
`python-dotenv` (читання `.env`) і або `requests`, або `openai`.

| Демо | Що потрібно |
| --- | --- |
| `000`, `001`, `013`–`015` | нічого: текстовий файл і shell-скрипти (`curl`, `jq`, `ollama`) |
| `002`, `004`, `006` | `requests`, `python-dotenv` |
| `003`, `005`, `007`–`009`, `011`, `012` | `openai`, `python-dotenv` |
| `010`, `010b` | `openai`, `pydantic`, `python-dotenv` |
| `016` | `langchain`, `langchain-openai`, `pydantic`, `python-dotenv` |

Тому файлів із залежностями два: `requirements.txt` (базовий) і
`requirements_langchain.txt` (він підключає базовий через `-r` і додає лише LangChain).
Якщо демо 016 на занятті не показується — важкий LangChain-стек ставити не треба.

## Порядок демо

### Шар 1. Просто HTTP: LLM API без жодної магії

| Файл | Що показує |
| --- | --- |
| `000_http_request.txt` | сирий HTTP-запит до `/v1/chat/completions` — усе, чим є «виклик LLM» |
| `001_curl_llm_request.sh` | той самий запит через `curl` + `jq` |
| `002_minimal.py` | те саме на `requests`: видно, що SDK нічого таємного не робить |
| `003_minimal_sdk.py` | той самий виклик через `openai` SDK — коротше      |

```bash
./001_curl_llm_request.sh
python 002_minimal.py
python 003_minimal_sdk.py
```

**Ідея шару:** LLM у чат-режимі — реактивна функція «запит → відповідь». Ані стану, ані дій.

### Шар 2. Пам'ять = список повідомлень

| Файл | Що показує |
| --- | --- |
| `004_minimal_chat.py` | діалог на `requests`: «пам'ять» — це просто масив `messages`, який ми щоразу надсилаємо повністю |
| `005_minimal_chat_sdk.py` | те саме через SDK |

```bash
python 004_minimal_chat.py    # порожній рядок = вихід
```

**Ідея шару:** ніякої «пам'яті» на боці моделі не існує — є контекстне вікно, яке ми наповнюємо самі.

### Шар 3. Tool calling і agentic loop

| Файл | Що показує |
| --- | --- |
| `006_minimal_agent.py` | перший агент на `requests`: `TOOLS` як рукописна JSON Schema, цикл `while`, ручний `tool_call_id` |
| `007_minimal_agent_sdk.py` | те саме через SDK: `message.tool_calls` замість копирсання в JSON |
| `008_minimal_agent_dispatch.py` | диспетчер `TOOL_FUNCTIONS` — інструмент стає звичайною Python-функцією |
| `009_minimal_agent_two_tools.py` | два інструменти → з'являється справжній вибір: агент сам вирішує порядок викликів; у логах видно Think → Act → Observe |

```bash
python 006_minimal_agent.py
python 009_minimal_agent_two_tools.py
```

**Ідея шару:** агент = LLM + інструменти + цикл. Модель не «виконує» нічого — вона лише
повертає намір (`tool_call`), а виконує його наш код. Ця межа має бути жорсткою.

### Шар 4. Структурований вивід

| Файл | Що показує |
| --- | --- |
| `010_minimal_agent_pydantic.py` | схема відповіді текстом у промпті + ручний `model_validate_json` + ретраї на невалідний JSON |
| `010b_minimal_agent_parse.py` | те саме силами SDK: `response_format=ReturnReport`, `pydantic_function_tool()`, `message.parsed`, `call.function.parsed_arguments` |

```bash
python 010_minimal_agent_pydantic.py
python 010b_minimal_agent_parse.py
```

> ⚠️ **`010b` потребує сильнішої моделі.** Strict `json_schema` — це фіча рушія
> інференсу, а не «розуму» моделі: дешеві маршрути її не мають і повертають 400
> (або, гірше, мовчки ігнорують і віддають прозу). Перевірено на **qwen3.7-plus**.
> `010` працює всюди, бо валідує відповідь сам.

### Шар 5. Запобіжники

| Файл | Що показує |
| --- | --- |
| `011_agent_limits_guardrails.py` | ліміт ітерацій, allowlist інструментів, валідація аргументів **до** виконання, no-progress detector |

```bash
GUARDRAILS=0 python 011_agent_limits_guardrails.py trap   # цикл без гальм
GUARDRAILS=1 python 011_agent_limits_guardrails.py trap   # з гальмами
```

**Ідея:** `[STOPPED_BY_LIMIT]` і `[FINAL_ANSWER]` — це два **різні** стани в логах.
«Вимушена зупинка» не є «успішним завершенням».

### Шар 6. Agent Spec

| Файл | Що показує |
| --- | --- |
| `012_agent_spec.py` | контракт агента: Goal / Tools / Policies / Constraints (+ non-goals) / Completion / Output |

Детально про запуск — у наступному розділі.

### Шар 7. Локальні моделі через Ollama

| Файл | Що показує |
| --- | --- |
| `013_ollama_cli.sh` | інтерактивний запуск моделі в терміналі |
| `014_ollama_web.sh` | рідне API Ollama (`/api/chat`) |
| `015_ollama_web_openapi.sh` | OpenAI-сумісний ендпоінт (`/v1/chat/completions`) — саме завдяки йому всі попередні демо працюють локально без правок коду |

Установка й моделі — див. наступний розділ.

### Шар 8. Те саме, але фреймворком

| Файл | Що показує |
| --- | --- |
| `016_langchain_create_agent.py` | увесь код 006–012 в одному виклику `create_agent` |

```bash
python 016_langchain_create_agent.py                 # зі структурованим виводом
STRUCTURED=0 python 016_langchain_create_agent.py    # без нього
```

> ⚠️ **Потрібна сильніша модель.** На дешевій моделі падає з `BadRequestError: 400`:
> `ToolStrategy` шле `tool_choice="required"`, а слабкі маршрути цей параметр не
> підтримують. Перевірено на **glm-5.2**. Або запускайте з `STRUCTURED=0` — цикл
> працює на будь-якій моделі з tool calling.

**Що зникає:** рукописна JSON Schema (будується з сигнатур і docstring), словник
`TOOL_FUNCTIONS`, цикл `while` з `messages.append`, ручна валідація фінального JSON.

**Що не зникає:** доменні запобіжники з 011 — allowlist бізнес-правил, детектор відсутності
прогресу, перевірка критерію завершення. Фреймворк дає **цикл**, а не **надійність**.

**Що протікає:** `response_format=ToolStrategy(...)` під капотом надсилає
`tool_choice="required"`, і не кожен провайдер це вміє — деякі відповідають 400, деякі мовчки
ігнорують. Уніфікований інтерфейс ховає різницю провайдерів, але не скасовує її: вона
вилазить пізніше і в менш очевидному місці.

## Ollama: локальні моделі

### 1. Установка

```bash
# Linux / WSL2
curl -fsSL https://ollama.com/install.sh | sh

# macOS
brew install ollama          # або .dmg з https://ollama.com/download

# Windows — інсталятор OllamaSetup.exe з https://ollama.com/download
```

Перевірка:

```bash
ollama --version             # демо перевірені на 0.18.0
```

### 2. Запуск сервера

```bash
ollama serve                 # слухає http://localhost:11434
```

На macOS і Windows сервер стартує разом із застосунком. На Linux після установки
скриптом він зазвичай уже піднятий як systemd-сервіс:

```bash
systemctl status ollama      # якщо активний, окремий `ollama serve` не потрібен
sudo systemctl enable --now ollama
```

Перевірка, що сервер живий:

```bash
curl http://localhost:11434/api/version
```

### 3. Завантаження моделей

Демо використовують дві моделі:

```bash
ollama pull qwen2.5:7b       # ~4.7 GB — для 015 і для агентних демо (tool calling)
ollama pull qwen3.5:4b       # ~3.4 GB — для 013 і 014, з режимом міркувань, який не завжди вдається вимкнути програмно
```

| Модель | Розмір | Де використовується | Чому саме вона |
| --- | --- | --- | --- |
| `qwen2.5:7b` | 4.7 GB | `015_ollama_web_openapi.sh`, `.env.ollama` | стабільний tool calling — на ній локально працюють демо 006–012 |
| `qwen3.5:4b` | 3.4 GB | `013_ollama_cli.sh`, `014_ollama_web.sh` | легка, має «думання», яке в демо вимкнено прапорцем |

Орієнтир по RAM/VRAM: 4B-модель — від ~4 GB вільної пам'яті, 7B — від ~8 GB.

Перевірка, що завантажилось:

```bash
ollama list
```

### 4. Запуск демо

```bash
./013_ollama_cli.sh          # інтерактивний чат у терміналі, вихід — /bye
./014_ollama_web.sh          # рідне API Ollama: POST /api/chat
./015_ollama_web_openapi.sh  # OpenAI-сумісне API: POST /v1/chat/completions
```

Прапорець `--think=false` у 013 і `"think": false` у 014/015 вимикають блок міркувань —
інакше модель спершу видає довгий внутрішній монолог, і на лекції це заважає.

### 5. Перемикання решти демо на локальну модель

```bash
cp .env.ollama .env
python 009_minimal_agent_two_tools.py
```

`.env.ollama` містить:

```
OPENAI_BASE_URL=http://localhost:11434/v1
OPENAI_API_KEY=ollama          # Ollama ключ не перевіряє, але SDK вимагає непорожній
LLM_MODEL=qwen2.5:7b
```

**Це і є суть демо 015:** жоден рядок Python-коду не змінюється — міняється лише
`OPENAI_BASE_URL`. Локальна модель підставляється замість хмарної тому, що Ollama
реалізує той самий OpenAI-сумісний контракт.

### 6. ⚠️ Локальні моделі слабкі — частина демо на них не піде

Моделі 4B–7B — не зменшені копії хмарних. Вони гірше тримають багатокроковий tool calling
(плутають порядок, забувають викликати другий інструмент) і не мають strict-режимів
структурованого виводу.

- `002`–`009`, `011`, `012` — працюють, для 011/012 слабка модель навіть наочніша:
  запобіжники й контракт спрацьовують частіше.
- `010b`, `016` — не працюють; запускайте на хмарній моделі
  (`qwen3.7-plus` і `glm-5.2` відповідно).

## Як запускати `012_agent_spec.py`

Скрипт має **два незалежні перемикачі**: змінну оточення `SPEC` (чи підставляти контракт
у system-промпт) і позиційний аргумент — ім'я завдання.

| Перемикач | Значення | За замовчуванням |
| --- | --- | --- |
| `SPEC` (env) | `1` — з контрактом, `0` — без нього (`NO_SPEC`, одне речення «ти агент підтримки») | `1` |
| аргумент | `ok` — штатний запит, `non_goal` — прохання поза межами контракту | `ok` |

### Три запуски на лекції

```bash
# 1. БЕЗ контракту — базова лінія
SPEC=0 python 012_agent_spec.py

# 2. З контрактом — те саме завдання
SPEC=1 python 012_agent_spec.py
#    те саме, бо SPEC=1 — значення за замовчуванням:
python 012_agent_spec.py

# 3. З контрактом + прохання поза межами (non-goals)
SPEC=1 python 012_agent_spec.py non_goal
```

Корисне четверте порівняння — показати, що без контракту межі не тримаються:

```bash
SPEC=0 python 012_agent_spec.py non_goal
```

### Що дивитися у виводі

Перший рядок логу — `[SPEC] увімкнена` / `[SPEC] ВИМКНЕНА`, далі `[TASK]` із текстом
завдання, потім `[TOOL_CALL]` / `[TOOL_CALL_RESULT]` по кроках і `[FINAL_ANSWER]` у кінці.

| Запуск | Очікувана поведінка |
| --- | --- |
| `SPEC=0` + `ok` | порядок дій випадковий: агент може відповісти «на око», пропустити `check_return_policy` або перевірити не всі замовлення; формат відповіді щоразу інший |
| `SPEC=1` + `ok` | порядок заданий політиками (спочатку `query_orders`, потім `check_return_policy` для **кожного** знайденого), критерій завершення перевіряється, формат стабільний |
| `SPEC=1` + `non_goal` | агент відмовляє: оформлення повернення й лист клієнту — у NON-GOALS, а контракт дозволяє лише читання |
| `SPEC=0` + `non_goal` | межі не тримаються: агент охоче «оформлює» повернення, якого не вміє оформлювати |

Оскільки поведінка моделі стохастична, різницю варто показувати **двома-трьома прогонами
поспіль** із `SPEC=0`: сенс не в одному «поганому» прогоні, а в розкиді траєкторій, який
контракт прибирає.

> Примітка: запуск із `SPEC=0` — це не «зламаний» варіант, а базова лінія. Порівняння
> двох логів поруч і є демонстрацією того, навіщо Agent Spec потрібен як версіонований
> артефакт, а не як рядок усередині f-string.

## Наскрізна лінія лекції

```
000–003   виклик LLM = один HTTP-запит
004–005   пам'ять = масив messages, який надсилаємо щоразу повністю
006–009   інструменти + цикл = агент; межа «намір / виконання» проходить по нашому коду
010–010b  структурований вивід: від промпта до гарантії провайдера (і її меж)
011       межі автономності: ліміти, allowlist, валідація, no-progress
012       контракт агента як артефакт, що версіонується
013–015   той самий код на локальній моделі, без правок
016       фреймворк: що він забирає, що віддає і де протікає
```

Порядок навмисний: спочатку видно, **що саме** фреймворк ховає, і лише потім — що він дає
натомість.
